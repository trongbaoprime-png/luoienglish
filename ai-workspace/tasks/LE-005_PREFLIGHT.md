## 2. Required Context & Architectural Boundaries
- **Domain Entity**: `ChildProfile` in `src/types/student.ts`:
  - `id: string`
  - `parentUid: string` (Strictly immutable)
  - `nickname: string` (Max 20 chars, sanitized, zero PII)
  - `avatarKey: string` (Whitelisted sloth avatar key, no custom image uploads)
  - `schoolGrade: number` (Preschool to Grade 5, values 0–5)
  - `englishLevel: EnglishLevel` ("A0" | "A1" | "A1+" | "A2")
  - `preferences: ChildPreferences` (`{ themeId: "cozy" | "explorer" }`)
  - `dailyGoalMinutes: number` (Default 15, max 60)
  - `createdAt`, `updatedAt`
- **Security Rules**: `firestore.rules` lines 50–66:
  - Create: `request.resource.data.parentUid == request.auth.uid`
  - Read: `resource.data.parentUid == request.auth.uid`
  - Update: `resource.data.parentUid == request.auth.uid && request.resource.data.parentUid == resource.data.parentUid`
  - Delete: `resource.data.parentUid == request.auth.uid`
- **Server Utility**: `authorizeChildAccess(trustedParentUid, childId, childRepo)` in `src/services/auth/serverAuth.ts`.

## 3. Threat Model & Failure Mode Analysis

| # | Threat / Failure Vector | Impact | Mitigation in LE-005 Design |
| :--- | :--- | :--- | :--- |
| **1** | **IDOR (Parent A edits Child B)** | Critical data breach | All API route handlers derive `parentUid` strictly from `verifyServerAccountSession()` and verify `child.parentUid === trustedParentUid`. |
| **2** | **Child Profile Hijacking** | Account takeover | `parentUid` is strictly immutable on update; Firestore rules reject mutations to `parentUid`. |
| **3** | **Unbounded Child Creation** | Resource exhaustion / DoS | Limit maximum 5 child profiles per parent account. |
| **4** | **PII / Unsafe Text Injection** | Child privacy violation (COPPA) | Disallow real full names, phone numbers, or free-form bio text; enforce strictly whitelisted sloth avatars. |
| **5** | **Sibling Theme Collision** | UI preference desync | Ensure theme is updated in `children/{childId}.preferences.themeId` and cached under `luoi_theme_${childId}`. |

## 4. Preflight Critic Evaluation (13 Questions)

1. **What does the server trust?** The verified `auth_session` / Firebase ID token.
2. **What is client-controlled?** `nickname`, `avatarKey`, `schoolGrade`, `englishLevel`, `dailyGoalMinutes`.
3. **What is the authorization source?** Server-verified token matching `child.parentUid`.
4. **Can Tenant A access Tenant B?** Blocked by `isParentOfChild` in Firestore and `authorizeChildAccess` on server.
5. **Can ownership change?** No, `parentUid` is rejected on update if different from existing.
6. **Can test code reach production?** No, `RepositoryFactory` uses real Firestore in production.
7. **What happens if secrets are missing?** Server fails closed (`500 ServerAuthError`).
8. **What happens on replay?** Idempotent update/create logic based on `childId`.
9. **What happens under concurrent requests?** Max child limit check runs with database transaction if necessary.
10. **Can direct navigation bypass UI?** `/parent/children` is guarded by Server Component layout requiring `auth_session` and `parent_mode_session`.
11. **Can stale session remain privileged?** No, layout enforces active unexpired session.
12. **Can client calculate trusted state?** No, timestamps and IDs are server-assigned/validated.
13. **What happens when network fails?** Optimistic UI rolls back cleanly on mutation failure.
